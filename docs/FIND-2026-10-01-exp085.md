## 3. ⚠️ The blocker, stated plainly

**The code is not public.** `t88take/rsna-knee-code` (referenced by the manifest as the place the
config/backbone live) returns **403 Forbidden**, and all 27 of `t88take`'s public kernels are from
other competitions — there is no public notebook with the model definition.

So the **weights are fully in hand and the forward pass is not**, and the shapes constrain it only
partly: `slice_pool` is evidently a depth-conditioned attention pool, and `head.out = Linear(256,12)`
with `head.query (12,256)` looks like a per-finding classifier applied to that finding's own 256-d
feature — but the exact ordering of norm / depth-add / softmax / slot mixing **cannot be read off the
shapes**, and two unknowns at once (the forward *and* the slice preprocessing) are hard to separate:
if a reimplementation scores 0.85 instead of 0.9062, we cannot tell which half is wrong.

## 4. What would make it usable, in order of cost

1. ⭐ **Ask the two questions that collapse the search.** The config dict names the *exact* recipe
   (`band_groups`, `n_group 4`, `per_study`, `crop_mm 130`, `slice_depth_range (0.2,0.8)`,
   `center`). Slice selection from those is reconstructible; **the head's forward is not.** Finding the
   author's `infer.py` (or a discussion post) is worth more than an hour of guessing.
2. **Constrain the forward with a known-answer test.** Run the reimplementation on *our* cached
   volumes and require **gold58 ≈ 0.9062**. That single number validates forward *and* preprocessing
   together — but only if the slices are right, which is why (1) matters.
3. **Fall back to the members whose code IS public.** `apoorvadixit/rsna-knee-weights-v4cx` is
   `convnext_small.in12k__latL__v4cx{0..4}_best.pt` (199 MB x5) — a **timm ConvNeXt-small**, i.e. a
   standard architecture whose forward is not in question, so only the head needs matching.
   `soyaoki/rsna-knee-my-models` is a 5-fold set (89 MB/fold, `_epoch5`/`_epoch10` variants).
   Neither has a published score, so each costs a CPU gate to price.

## 6. ⚠️ Verification: three claims re-checked with real exit codes

Prompted by the observation that PowerShell shows red when it should not — and that every command in
this session was piped through `Select-Object` / `Select-String`, so **the exit code was never checked
once**.

**`Select-Object -First N` — and any early-terminating pipeline stage — KILLS the upstream process, so
PowerShell reports a non-zero exit code.** A truncation is therefore *indistinguishable* from a real
failure. Three load-bearing commands were re-run with output redirected to files:

| command | exit | stderr | verdict |
|---|---|---|---|
| `work/inspect_ckpt.py work/newckpt/fold0.pt` | **0** | empty | ✅ and the output is **bit-identical across two runs** |
| `scripts/lb_ceiling.py` | **0** | empty | ✅ rank 578 / 4692, 0.943, board max 0.961 — as reported |
| `gate_pair.py dt_d27_624 vs d27_528`, 12 games | **0** | 10,480 B | ✅ result **2-10-0 → `d27_528` wins**, and the stderr is *entirely* the OpenSpiel game list that `kaggle_environments` prints on import, twice, with **zero real error lines** |

⇒ **The §1–§5 conclusions stand**, and the two displayed red exit codes were the pipe, not the commands.

⚠️ **But the practice was wrong and is now a rule:**
1. **Redirect to a file and read the file.** Do not truncate a pipeline whose exit code matters.
2. **Print `$LASTEXITCODE` explicitly**, in the same message as the conclusion drawn from it.
3. **Read stderr even when stdout looks right** — and know that this repo's most common stderr is
   benign: `kaggle_environments` prints ~10 KB of OpenSpiel game names on import.
4. **Prefer a reproducibility check** (run twice, diff) over eyeballing.
5. This is the same bug class as the failed import, the dropped `ACTION6` coordinate and the refused
   `kernels_push`: **a silently-swallowed failure reported as success**, one level up. Given how often
   that class has produced a wrong finding here, an unchecked exit code is not a style issue.

## 7. Forward-pass reconstruction: the ARCHITECTURE is proven, the ORDER is still a hypothesis

### 7.1 ✅ Proven: the module tree matches the checkpoint exactly

`work/exp085_model.py --selftest` (exit **0**, empty stderr):

```
checkpoint tensors      : 245
reconstructed parameters: 245
MISSING (in model, not in ckpt)  : 0  []
UNEXPECTED (in ckpt, not in model): 0  []
strict=True load: PASS  <-- the module tree matches the checkpoint EXACTLY
shape mismatches on shared names: 0 []
```

**`load_state_dict(strict=True)` over all 245 tensors is a real proof, not a plausibility argument**:
every parameter name and shape must match, including the bare `Parameter`s
(`slice_pool.query`, `head.query`, `head.slot_emb`, `head.slot_prior`) that have no `.weight` suffix and
therefore no shape hint from their name. The recovered tree is:

```
mean, std                                   (1,3,1,1)   ImageNet buffers
backbone.net                                HF Dinov2Model, config image_size 518 (see 7.2)
slice_pool.norm                             LayerNorm(1536)
slice_pool.depth_mlp                        Linear(1,256) -> SiLU -> Linear(256,1536)
slice_pool.key / value                      Linear(1536,256) / Linear(1536,1536)
slice_pool.query                            Parameter(12,256)   one query per FINDING
head.proj                                   LayerNorm(1536) -> Linear(1536,256)
head.out                                    Linear(256,12)
head.query / slot_emb / slot_prior          Parameter(12,256) / (6,256) / (12,6)
```

### 7.2 ⚠️ Two real bugs found on the way, both caught by exit codes

1. **`transformers` could not import DINOv2 at all**: `RuntimeError: operator torchvision::nms does
   not exist`. The cause is not transformers — **`torchvision 0.28.0+cu126` was installed against
   `torch 2.7.0+cu126`**, and 0.28 pairs with torch 2.12, so its C++ extension registers against the
   wrong ABI. torch 2.7.0 pairs with torchvision **0.22.0**; installing that (`--no-deps`) fixed the
   import.
2. **The backbone must be built at `image_size=518`, not 224.** The checkpoint's
   `backbone.net.embeddings.position_embeddings` is **(1, 1370, 768)** = 1 + 37², i.e. HF's default
   Dinov2Config grid, and the 224 forward works by **interpolation**. Building it at 224 gives
   (1, 257, 768) and the load fails with a size mismatch. `img: 224` in the config is the *input* size,
   not the backbone's — an easy and silent-confusion-inducing distinction.

⚠️ Both were found **only because `$LASTEXITCODE` was checked** — the first produced 9,194 bytes of
stderr behind a traceback, which the previous session's `Select-String` habit would have filtered.

### 7.3 ⚠️ Still a HYPOTHESIS: the order of operations

Three readings are implemented and switchable (`--forward A|B|C`); all three execute (exit 0, empty
stderr) and return `(B, 12)` logits:

| order | logits on random input | reading |
|---|---|---|
| **A** | `[-17.2, 12.7]` | per-finding classifier: `logit_f = out.weight[f]·h_f + out.bias[f]` |
| B | `[-0.32, 0.19]` | A, preceded by a soft mixture over the 6 slots |
| C | `[-216, 155]` | findings attend slots via `head.query`, then a shared `Linear(256,12)` |

A's range looks most like trained logits and C's explodes, but **that is not evidence** — only a
numeric test on real data can decide, which is why all three are kept runnable rather than one guessed.

### 7.4 The next step, and why it needs Kaggle

There are **no MRI volumes on this machine** (the corpus lives in the Kaggle datasets), so the deciding
experiment must run there: a **CPU kernel** that builds the 12-slice inputs from the corpus per the
checkpoint's own config (`band_groups`, `n_group 4`, `per_study`, `center`, `crop_mm 130`,
`slice_depth_range (0.2,0.8)`), runs **all three orders**, and reports **gold58 macro-AUC** for each.

That single run decides three things at once:
* whether the reconstruction works on real data at all (a broken head reads ≈ **0.5**, not ≈ 0.9);
* **which forward order is correct** — the one that reaches ~0.9062;
* whether we can reproduce the author's number, which is the precondition for using it as a member.

**crop 336 / `linspace` = 0.7929, bit-for-bit the first run's number.** That is a genuine

### 8.2 ⚠️ All three "band" readings are WORSE, and the crop barely matters

* every band policy loses to plain `linspace` at every crop (0.7553–0.7851 against 0.7861–0.8020);
* the crop scale moves the result by at most **0.016** across 240–336 px, so `crop_mm 130.0` is **not**
  the missing 0.10 either.

⇒ **Two of the three candidate explanations for the 0.7997 → 0.9062 gap are now eliminated**: it is
neither *which* slices are chosen nor *how tightly* they are cropped.

### 8.3 ⭐ What the config points at instead

⚠️ Every experiment so far, mine included, has computed **one** forward pass over all 12 slices and
attended across them. But the checkpoint's config says:

```
n_group 4 | group_pick per_study | eval_group_agg mean      <- "mean" aggregation over GROUPS
slice_attention_queries 1 | target_specific_slice_attention True
```

**`eval_group_agg: mean` is an aggregation over FOUR GROUPS, not over 12 slices.** The natural reading
-- and the one that would explain a systematic ~0.10 shortfall -- is that the model is applied **once
per group of 3 slices**, producing 12 logits per group, and the final prediction is the **mean of the
4 groups' logits**. The depth encoding (`slice_pool.depth_mlp`) may likewise be the **within-group**
depth rather than the global depth, since `group_pick: per_study` picks groups independently.

That is a different computation over the same weights, it is cheap to test with the caching design
already in place, and **it is the only remaining structural difference between our forward and the
author's.**

### 8.4 Next run, concretely

Same harness, `linspace` at the best crop, varying only the aggregation:

1. **pool 12 -> head** (the current control, 0.8020);
2. **4 groups x 3 -> head -> mean of logits** (`eval_group_agg: mean`, global depth);
3. **4 groups x 3 -> head -> mean of logits**, **within-group depth**;
4. as 2/3 but `max` and `median` aggregation as controls.

If (2) or (3) reaches ~0.90, the reconstruction is complete and exp085 clears the A167 member gate;
if all four land at ~0.80, the gap is in the corpus preprocessing itself (`train_window_sampling:
overlap`, the windowing/intensity convention) rather than in anything the config names.

## 9. Third gate run: `eval_group_agg: mean` CONFIRMED — and the last 0.087 is the CORPUS, not the config

`ppxl16/rsna-knee-exp085-group-agg` v1 ran to **COMPLETE** (exit 0, no failure, ~24 min CPU).

### 9.1 ✅ The control reproduces for the THIRD time

```
crop    pool12      grp_mean_global  grp_mean_local  grp_max_global  grp_median_global
272     0.8020      0.8182           0.8191          0.7997          0.7890
336     0.7929      0.8178           0.8064          0.7841          0.8002
```

**`pool12` at crop 272 = 0.8020 and at crop 336 = 0.7929** — bit-for-bit run 2's and run 1's numbers,
now across **three different kernel versions**. The instrument is stable, which is what makes the rest
of this readable.

### 9.2 ⭐ The config's word was right: the groups are aggregated by MEAN

**`grp_mean_*` beats `pool12` at both crops** (+0.016 to +0.025), and — the part that makes it a
*finding* rather than a lucky cell — **`grp_max` and `grp_median` do NOT**: they land at or below the
pooling control (0.7997/0.7841 and 0.7890/0.8002). So the gain is specific to **mean aggregation over
the four groups**, which is exactly what the checkpoint's `eval_group_agg` field says. The model is
evaluated **once per group of 3 slices**, and the four groups' logits are averaged.

That is the second structural piece recovered from the config alone, after the head order (§2):
* **order A** (per-finding classifier): +0.13 over B/C;
* **per-group mean aggregation**: +0.02 over pooling 12 slices at once.

### 9.3 ⚠️ And that is where the config runs out: 0.8191 against 0.9062

Best cell **crop 272 / `grp_mean_local` = 0.8191**; crop 336 / `grp_mean_global` = 0.8178. The gap to the
author's **0.9062 is 0.087**, and **every knob the checkpoint names is now settled**:

| knob | status |
|---|---|
| head order (A/B/C) | ✅ **A**, measured, +0.13 |
| `eval_group_agg` | ✅ **mean**, measured, +0.02 (and max/median ruled out) |
| `n_group` / `group_pick` | ✅ 4 groups of 3, per study |
| `slice_depth_range (0.2,0.8)` | ✅ central 9–34 |
| `slice_select band_groups` | ❌ **eliminated** — all three band readings are worse than even spacing |
| `crop_mm 130.0` | ❌ **eliminated** — 240→336 px moves the result by ≤0.016 |
| `img 224`, `slice_feature_dim` 1536 | ✅ CLS ⊕ mean-patch, 224 px |

⇒ **The remaining 0.087 cannot be attributed to anything in the config.** The only input left that we
are *not* reproducing is **the corpus preprocessing itself**: `knee-raptor-corpus` is this repo's cached
volumes (uint8 0–255, 336×336, 44 slices), and there is no evidence it is the pipeline exp085 was
trained on. `train_window_sampling: overlap` and the windowing/intensity convention are exactly the
things a checkpoint cannot tell us and a config field only names.

### 9.4 The next cheap tests, in order of prior

1. **depth-axis reversal** — if index 0 is the other end of the stack, every slice is misplaced and the
   depth encoding is inverted; one run, and a large effect if true;
2. **intensity convention** — `/255` was chosen from the data (max 255) and logged, but their pipeline
   may apply a knee window before scaling; test 2–3 monotone transforms;
3. **slice count / spacing within the range** — 12 is confirmed, but `band_groups` may mean the bands
   are *sampled* rather than *evenly divided*, which §8's three readings did not cover;
4. **only then** conclude that exp085 needs the author's own preprocessing, in which case it is out of
   reach without the private `rsna-knee-code` and the line should be closed honestly.

⚠️ **Status of the goal, stated plainly:** exp085 is at **0.8191**, the A167 member gate is **solo ≥ 0.90**,
and the author's number is **0.9062**. The reconstruction is now *structurally* complete and *numerically*
0.087 short; **exp085 is not usable as a member yet**, and it will not be until the input pipeline is
matched.

  whose author has just withdrawn it. **That is not a thing this project should do**, and it is worth

### 10.3 What was actually recovered, and what it is worth

| piece | how | result |
|---|---|---|
| module tree | 245/245 tensors, `strict=True`, 0 missing, 0 unexpected | ✅ proven locally **and** on Kaggle |
| **head order** | A vs B vs C, measured | ✅ **A**, +0.13 over B/C |

**0.8191 is below the A167 member gate (solo ≥ 0.90), so exp085 was never usable as a member**, and the
last 0.087 was traced to the corpus preprocessing — the one component that needed the author's own
code, which is private.

### 10.4 ⭐ The transferable lessons, which are worth more than the checkpoint

1. **A checkpoint is self-describing, and reading it beats guessing.** The config dict gave the head
   order, the group structure, the depth range, the crop and the resolution; two of those were
   recovered **as measurements** (+0.13 and +0.02) rather than assumptions.
2. **A shape-compatible, strictly-loading model can still be 0.09 wrong** — architecture is not a
   forward pass, and the forward pass is not the input pipeline. Three separate layers, each needing
   its own experiment.
3. **A public dataset can stop being public at any time.** Anything a submission must mount should be
   copied to a dataset **we** control *at the moment we first use it*, not at submission time. This
   project lost the ability to submit exp085 because it planned to keep attaching someone else's
   dataset — that is a planning failure, not bad luck.
4. ⚠️ **`kernels_push` reports success while silently dropping a dataset source it cannot attach.** It
   did not raise; it printed "successfully pushed". That is the same swallowed-failure class as the
   refused push and the dropped `ACTION6` coordinate, and the only defence is to read the warning
   output and assert the mount inside the kernel (which `--selftest`-style checks do).

### 10.5 The fourth kernel's failure, confirmed and attributed

`rsna-knee-exp085-axis` finished in **ERROR**. Its log is one line:

```
!! exp085 fold0.pt not mounted
```

**That is this kernel's own guard, firing exactly where it should** — the checkpoint dataset was
dropped from the push (§10.1), so the run stopped before loading anything.

⚠️ **Two things worth separating:** (a) the *cause* is the withdrawn dataset, not a defect in the new
axis/intensity variants — **that code was never executed**, so it is syntax-checked and unproven
rather than wrong; (b) **the guard is the reason the failure is readable**. A kernel that built the
model first and discovered the missing file inside a traceback would have produced the same ERROR
status with a far worse diagnosis. `raise SystemExit("!! ... not mounted")` on a required input is
worth the four lines it costs.

⚠️ **And the push said "successfully pushed".** The only reason this did not become another
swallowed failure is that the warning text — *"The following are not valid dataset sources and could
not be added"* — was read. **`kernels_push` cannot be trusted to fail; its output must be read.**
