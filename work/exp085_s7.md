**`load_state_dict(strict=True)` over all 245 tensors is a real proof, not a plausibility argument**:
every parameter name and shape must match, including the bare `Parameter`s
(`slice_pool.query`, `head.query`, `head.slot_emb`, `head.slot_prior`) that have no `.weight` suffix and
therefore no shape hint from their name. The recovered tree is:

```
mean, std                                   (1,3,1,1)   ImageNet buffers
backbone.net                                HF Dinov2Model, config image_size 518 (see 7.2)
slice_pool.norm                             LayerNorm(1536)
slice_pool.depth_mlp                        Linear(1,256) -> SiLU -> Linear(256,1536)
slice_pool.key / value                      Linear(1536,256) / Linear(1536,1536)
slice_pool.query                            Parameter(12,256)   one query per FINDING
head.proj                                   LayerNorm(1536) -> Linear(1536,256)
head.out                                    Linear(256,12)
head.query / slot_emb / slot_prior          Parameter(12,256) / (6,256) / (12,6)
```

### 7.2 ⚠️ Two real bugs found on the way, both caught by exit codes

1. **`transformers` could not import DINOv2 at all**: `RuntimeError: operator torchvision::nms does
   not exist`. The cause is not transformers — **`torchvision 0.28.0+cu126` was installed against
   `torch 2.7.0+cu126`**, and 0.28 pairs with torch 2.12, so its C++ extension registers against the
   wrong ABI. torch 2.7.0 pairs with torchvision **0.22.0**; installing that (`--no-deps`) fixed the
   import.
2. **The backbone must be built at `image_size=518`, not 224.** The checkpoint's
   `backbone.net.embeddings.position_embeddings` is **(1, 1370, 768)** = 1 + 37², i.e. HF's default
   Dinov2Config grid, and the 224 forward works by **interpolation**. Building it at 224 gives
   (1, 257, 768) and the load fails with a size mismatch. `img: 224` in the config is the *input* size,
   not the backbone's — an easy and silent-confusion-inducing distinction.

⚠️ Both were found **only because `$LASTEXITCODE` was checked** — the first produced 9,194 bytes of
stderr behind a traceback, which the previous session's `Select-String` habit would have filtered.

### 7.3 ⚠️ Still a HYPOTHESIS: the order of operations

Three readings are implemented and switchable (`--forward A|B|C`); all three execute (exit 0, empty
stderr) and return `(B, 12)` logits:

| order | logits on random input | reading |
|---|---|---|
| **A** | `[-17.2, 12.7]` | per-finding classifier: `logit_f = out.weight[f]·h_f + out.bias[f]` |
| B | `[-0.32, 0.19]` | A, preceded by a soft mixture over the 6 slots |
| C | `[-216, 155]` | findings attend slots via `head.query`, then a shared `Linear(256,12)` |

A's range looks most like trained logits and C's explodes, but **that is not evidence** — only a
numeric test on real data can decide, which is why all three are kept runnable rather than one guessed.

### 7.4 The next step, and why it needs Kaggle

There are **no MRI volumes on this machine** (the corpus lives in the Kaggle datasets), so the deciding
experiment must run there: a **CPU kernel** that builds the 12-slice inputs from the corpus per the
checkpoint's own config (`band_groups`, `n_group 4`, `per_study`, `center`, `crop_mm 130`,
`slice_depth_range (0.2,0.8)`), runs **all three orders**, and reports **gold58 macro-AUC** for each.

That single run decides three things at once:
* whether the reconstruction works on real data at all (a broken head reads ≈ **0.5**, not ≈ 0.9);
* **which forward order is correct** — the one that reaches ~0.9062;
* whether we can reproduce the author's number, which is the precondition for using it as a member.
